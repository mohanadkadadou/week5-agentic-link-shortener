# Week 4 Writeup: Structuring a Repo for Agents (Link Shortener)

**Mohanad Kadadou (2309115218).** Agent: Claude Code. Feature: task 2, Click counter. Full evidence: [`docs/DETAILS.md`](docs/DETAILS.md) and [`docs/transcripts/`](docs/transcripts/).

**1. `AGENTS.md`.** About 60 lines: what the service is, a file map, install/run/test commands, conventions (parameterised SQL, type hints), a plan → failing test → implement → verify → review workflow, safe / ask-first / forbidden commands, and gotchas (tests share one `links.db`; `init_db()` runs at import and never adds columns to an old database). It is broadly available because every task needs it. `intent.md` adds the purpose, five invariants and non-goals that a reviewer checks against.

**2. Scoped instruction.** `tests/AGENTS.md` holds the testing rules: go through the public API, cover success and failure, keep tests independent (they share one database), assert behaviour not implementation, and show the test failing first. It applies only when working on files under `tests/`, so feature tasks that never touch tests don't carry it in context. Claude Code reads `AGENTS.md` through a one-line `CLAUDE.md` (`@AGENTS.md`); nested instruction files are picked up when the agent works in that directory. Antigravity and Gemini CLI read `AGENTS.md` or `GEMINI.md` the same way.

**3. Reusable workflow.** `.claude/skills/implement-feature/SKILL.md` encodes the seven steps: read the task and guidance, inspect code and tests, state behaviour and affected files, write a failing behavioural test, make the smallest change, run `scripts/check.sh`, and summarise risks. Claude Code exposes it as an Agent Skill, discovered from its description or invoked by name. A `/test-summary` command and a pre-commit hook (ruff + pytest, which blocked my bad commits) complement it.

**4. Plan, implement, review.** The plan stage was a read-only planner subagent, the implement stage a subagent that followed the same steps the skill encodes, and the review stage a read-only reviewer. Honest caveat: I codified the skill after the first run and then restructured the repo to the final layout, so the skill was never invoked by name. The final reviewer returned **ACCEPT**. Subagents were launched with the Agent tool using role prompts; `.claude/agents/` is committed for future sessions.

**5. What the agent found.** The planner raised the real risk: an existing `links.db` has no `clicks` column, so it designed an idempotent `ALTER TABLE` migration and a migration test. The first reviewer found that `UPDATE … RETURNING` needs SQLite 3.35 or newer (older systems would return 500 on every redirect) and that one test was vacuous. I fixed both and recorded each decision.

**6. What I learned.** Put stable facts, such as the shared database and the migrate-never-drop rule, in files that load every session, and put narrow rules where they apply. A planner that reads those files produces a safer plan than a bare prompt, and a deterministic hook beats prose rules. A subagent's report is only a claim, so I re-read the diff and re-ran the checks myself.
